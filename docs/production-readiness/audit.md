# BeOnGym production readiness audit

Baseline: `31d90ff`, 11 September 2026. Decision: **NOT READY**.

This is a code-based audit, not a certification or evidence of successful production operation. Repository structure, package/configuration, schema and migration history, authentication and authorization helpers, all server actions and API routes, page loaders, domain data modules, payment lifecycle, directory/globe code, deployment workflow and existing checks were inspected. UI behavior across devices, external provider behavior, restores and deployment remain unverified until exercised. No application code was changed before this report. Local database inspection was read-only: 12 gyms, 47 users, 34 orders, 24 applied migrations; the checked profile/subscription tenant mismatches and duplicate open visits were zero. This is not an inspection of production data.

## Product and architecture

Next.js 16.3.4 App Router, React 19, custom signed-cookie authentication with bcrypt/jose, Prisma 7 with PostgreSQL adapter, Zod, server actions and Dodo hosted checkout. Preserve this architecture. Server pages load domain data in `lib/data`; interactive components submit server actions. The proxy supplies navigation/paywall checks; it is not sufficient authorization for actions or data loaders. Operational actions generally use paid staff/owner guards and explicit ownership assertions. There are distinct prospect, owner, staff, member and platform-admin roles. Public directory projections and checkout return pages cross sensitive boundaries.

The owner workspace covers clients, sold memberships, payments, visits, classes, leads, assisted WhatsApp and staff. Members have a separate portal. SaaS billing is separate from payments recorded by a gym. Public business listings, claim and listing flows feed account creation. The canvas/d3 globe and accessible directory already exist; improve them rather than replacing them. Marketing currently underplays the globe and directory membership is tied to paid access. No automated messaging provider or secure invitation delivery exists.

The schema has useful tenant indexes, unique member codes, booking occurrence uniqueness, claim/owner partial indexes and webhook event uniqueness. Separate gym/profile foreign keys do not prove tenant consistency. Financial records have mixed deletion rules. Serializable transactions protect some operations but not checkout fulfilment, owner mutation, attendance or renewals. Historical migrations include destructive drops/data resets; never edit or replay them casually against an existing database.

## Findings

P0 blocks launch; P1 should be fixed before launch; P2 follows launch; P3 requires customer evidence. Complexity: S (localized), M (several modules), L (schema/workflow/testing). File paths are relative to repository root. Dependencies identify implementation order, not permission to defer a launch blocker.

## Phase implementation plan

Execute the user's revised sequence. Every phase records changed files, tests, failures, risks and deferred external work in `progress.md`. During verification make only fixes needed to pass that phase's gate. Use isolated fixtures; never reset the existing database. Do not claim exhaustive behavioral coverage from source inspection.

1. Central configuration policy, explicit runtime distinctions, guarded fixtures, reproducible Prisma commands and regression tests.
2. Verify official Dodo event contract; lock/validate order and event transitions, preserve suspension/history, scope return flow, remove implicit simulation. Claim payment requires independent ownership approval.
3. Shared atomic limiter; close public attachment; strict sessions/redirects/password bounds and request-origin checks.
4. Live tenant/profile binding, public projections and hostile resource matrix across roles.
5. Preflight schema additions, preserve financial records, constrain races, repair booking/renewal atomicity; backup runbook.
6. Minimal transactional audit log with tenant ownership and secret-safe metadata.
7. Expiring one-time invitations, revocation/regeneration and explicit delivery state; atomic owner policy.
8. Compatible member-code authentication and secure recovery/session lifecycle.
9. Globe flagship: bounded public discovery, honest profiles/claims, search/types/focus, lazy rendering, accessible mobile/theme fallback and acquisition events.
10. Shared membership date rules; expiring/overdue/inactive follow-up list and renewal outcomes.
11. Honest assisted communication with preferences and future provider adapter.
12. Fresh owner checklist; public profile completion and actionable dashboard.
13. Currency/history correctness; responsive/loading/error/empty/accessibility verification without rebranding.
14. Measure and bound operational/admin queries; justified indexes and bundles.
15. Public canonical metadata, sitemap, robots and structured data.
16. Audited admin claim decisions, account controls and bounded lists.
17. Safe structured errors, health/readiness and incident documentation.
18. Data inventory, export/deletion requests/preferences and accurate policy drafts requiring legal review.
19. Browser/action/payment/tenancy negative E2E tests on disposable database, CI gates.
20. Staging migration/restore, sandbox billing and domain/session/email/job rehearsal. External credentials and actual provider evidence are required.
21. Re-audit all remaining P0/P1 with evidence; answer the ten CTO questions. Recommend a measured 30-day first-customer plan, not speculative feature development.

## Baseline verification and limits

`npm run lint` and `npm run typecheck` passed on the existing installation. No production build, browser interaction, live payment, delivery or restore has been certified. Existing test scripts must run on a disposable database before their results can be used. The current data was not seeded/reset. `.vscode/` was already untracked and is preserved.
